# 真实格式样例（数据全部合成）

这两个文件的**结构**照抄支付宝 / 微信 PC 端实际导出的形态，**内容全部是编造的**，
不含任何真实用户交易。

## 为什么需要它们

`fixtures/synthetic_ledger.json` 验证的是「金额口径与去重逻辑」，它已经是规整 JSON，
证明不了「真实导出文件能不能解析」。这里补的就是这一环：

| 仿真点 | 具体形态 | 不处理会怎样 |
| --- | --- | --- |
| 表头不在第一行 | 支付宝前 4 行、微信前 11 行是说明文字 | 按固定行号取表头，得到一堆 `账号:[...]` |
| 编码 | 支付宝可能是 GBK，微信是带 BOM 的 UTF-8 | 中文列名乱码 → 表头永远找不到 |
| 列名含全角括号 | `金额（元）` | 按 `金额(元)` 精确匹配会失败 |
| 列名带尾随空格 | `交易号 ,商家订单号 ,` | 同上 |
| 金额带符号与千分位 | `¥1,234.56` | `float()` 直接抛异常 |
| 交易关闭行 | 美团那笔赔付后关闭，钱没真正发生 | 会被当成支出入账 |
| 0 元订单 | 积分兑换 | 契约要求 `amount_fen >= 1`，确认时整批 422 |
| 尾部说明行 | `以上记录以支付宝系统为准` | 被当成坏行报错 |
| 同一订单多次事件 | 微信美团订单「已全额退款」 | 只按订单号去重会误删原交易 |

## 预期解析结果

支付宝样本：6 条有效草稿（白菜 2 行被跳过——交易关闭 + 金额为 0）。

微信样本：6 条有效草稿。

两个文件都是 2026-11 月，合并后月度口径应为：

| 指标 | 值（分） | 说明 |
| --- | --- | --- |
| 收入 | 1002000 | 工资 10000.00 + 红包 20.00 |
| 毛支出 | 292750 | 32 + 4 + 129 + 2500 + 35 + 28.5 + 199 + 50 + 86 |
| 退款 | 500 | 淘宝退款 5.00 |
| 净支出 | 292250 | 毛支出减退款 |
| 收支差额 | 709750 | 收入减净支出 |

微信那笔「已全额退款」的 50.00 仍按支出计入（钱确实付出去过），退款在微信账单里
是另一条独立记录。这是刻意的保守处理：**没有可靠退款事件号时不做推断**（docs/13）。

## 真实样本到位后

把真实导出放到 `data/private/`（`.gitignore` 已排除，**永远不会进仓库**），
用 `python -m app.tools.parse_probe 文件路径 --source alipay` 打印解析结果，
逐笔与人工核对条数和金额。核对记录写进 `docs/20_parse_verification.md`。
