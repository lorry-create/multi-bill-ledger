# 队友 B 数据与 AI 开发任务书

目标是完成真实账单文件解析、截图字段识别和可解释分类，并提供能被后端直接调用的 Python 模块。负责 backend/app/intelligence 和 backend/tests/intelligence，不单独创建 API、数据库或用户系统。

先读 README、AGENTS、01、02、contracts/openapi.json，按 06 执行 T01、T04、T06。共用模型由 T00 提供；不可为了方便另造不兼容金额字段或枚举。

## 文件解析 T01

取得支付宝和微信真实导出样本，记录来源、导出日期、编码、表头和适配范围。处理说明行、Excel 日期、金额符号与分隔、交易号字符串、无效或失败交易。解析器只产出 ParseResult，不能静默跳过坏行。

共同支持 CSV 和 XLSX，不承诺一个平台两种格式都存在。真实样本在 data/private，Git 仅保留合成 fixture、适配说明和授权脱敏证据。源文件若改变表头要报不支持或明确错误，不能把列错位后当成功。

## 分类 T04

输入草稿及后端已限定为本人的个人规则。按个人规则、通用规则、DeepSeek、pending 顺序处理。normalize_merchant 的行为见 02，与后端建立规则时相同。

DeepSeek 使用官方 API，实际模型名记录在配置及实验报告。限制允许类别、解析 JSON、校验字段、有限重试。API 超时、空响应、截断和未知类别不输出虚构的确定结果。只发送必要脱敏字段，不让账单文本控制数据库或文件操作。

记录调用耗时和用量；规则和测试替身不能标 deepseek。CI 不带真实 API key、不访问收费服务；真实连通性、费用和效果另用受控样本验证。

## 截图 OCR T06

11 月 8 日前做小样本比选，选一个可在目标环境部署或调用的 OCR 主方案。截图输出一个或多个 TransactionDraft，保留原始识别和字段问题。未知日期年份、金额或方向留空等待确认，不能默补而不提示。

截图“识别成功”与“正确入账”不同。后端负责确认、去重和存储，前端负责对照修正。模型具备图像能力与否取决于实际端点和型号，未经真实调用不能写已支持。

## 实验与交付

目标至少 100 条人工核对交易、20 张真实截图。固定开发集和测试集；分别报告规则与规则加模型的分类准确率、待确认率、样本量和实际耗时。OCR 报告首次金额、日期、商户字段结果，人工修正后结果另列。

内部优化目标：OCR 金额至少 95%、日期至少 90%，分类至少 85%；这些不是已测结果和比赛规定，未达时如实报告。个人规则效果另用新交易验证，不能拿用户已修正的记录充当独立测试。

PR 必须包含函数交接、真实支持范围、运行命令、输入与输出、测试和失败样例。只有通过 11 月 15 日核心验收后，才有一天尝试实际可行的 RPA 路径；没有实际导出入口就不承诺自动导出。

## 新版DTO交接

必读13的四个内部函数及11的TransactionDraft、ParseResult、ClassificationResult、ClassificationRule和Issue模型。ClassificationResult现在含issues，规则类别使用不含pending的ResolvedCategory；未知分类输出pending结果并标明来源，而不是创建pending规则。

金额时间未知用草稿模型允许的null，确认前由用户补齐。输出不包含数据库连接、HTTP Response或自己定义的data包装。交付时给H一个输入、完整返回和一个失败返回，让H可直接导入调用。
